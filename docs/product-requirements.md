# データ移行支援Webアプリ プロダクト要件書

## 1. プロジェクトの概要

本プロジェクトでは、業務で受領したExcel・CSVデータを分析・整形し、データベースへ投入できるCSVへ変換するWebアプリを開発する。

特定の業界だけに依存しない汎用的なアプリを目指す。不動産データは最初のデモケースとして使用するが、実際の業務データは使用せず、すべて架空のサンプルデータを用いる。

また、本プロジェクトは、実務で発生するデータ移行の準備工程を整理し、安全で再現可能なワークフローとして提供することを目指す。

## 2. プロジェクトの背景

実務では、不動産会社から受領した約3,000件の物件Excelデータを整理し、データベースの各テーブルに対応するCSVを作成して、本番データベースへ投入する作業があった。

元データには、物件名、住所、建設会社、分譲会社、交通情報、URL、学校区、築年月、階数、ペット可否、タワーマンション判定、駐車場種別など、多様な項目が含まれていた。しかし、入力者ごとに表記や入力形式が異なり、そのままではデータベースへ投入できなかった。

そのため、表記の統一、重複データの確認、必須項目や形式の不備の確認、関連データの切り分け、テーブルごとのCSV作成に多くの手作業が必要だった。この経験をもとに、同様のデータ移行作業を安全かつ再現可能にする支援アプリを企画する。

## 3. 解決する課題

- Excel・CSVの列名、表記、日付、真偽値などの入力形式が統一されていない。
- 空欄、不正な形式、想定外の値を人が目視で探す必要がある。
- 同じ対象を表すデータが複数存在しても、表記揺れによって重複を見つけにくい。
- 一つの表に混在した情報を、データベースの複数テーブルへ分ける作業が複雑である。
- 手作業による修正は、作業者ごとの差や修正漏れが生じやすく、同じ手順を再現しにくい。
- 元データ、変換ルール、エラー内容、出力結果の関係を追跡しにくい。
- 本番データベースへの投入直前まで問題が見つからない場合がある。

## 4. 想定ユーザー

### 主なユーザー

- 顧客や取引先から受領したExcel・CSVを整理する業務担当者
- データベース移行や初期データ登録を担当するエンジニア
- データの品質確認を担当する人

### MVPで想定する利用条件

- ユーザーは、入力データの業務上の意味と、出力先テーブルの項目を理解している。
- ユーザーは、アプリの提案を確認し、最終的な変換ルールや重複判定を自分で決定する。
- アプリだけで本番移行を完結させず、出力CSVを人が確認してから別の手順で投入する。

## 5. アプリが提供する価値

- データの問題を一覧化し、目視確認の負担と見落としを減らす。
- 変換ルールを画面上で明示し、誰が作業しても同じ結果を再現しやすくする。
- 元の値と変換後の値を比較できるようにし、意図しない変更に気づきやすくする。
- データベースの構造に合わせて出力を分割し、投入前の準備を効率化する。
- エラーの行、列、理由を示し、修正すべき箇所を特定しやすくする。
- 自動処理の結果を人が確認して確定する流れにより、効率と安全性を両立する。
- データの取り込みからテーブル別CSVの出力までを一つの流れで管理し、移行準備全体の進捗を把握しやすくする。

## 6. MVPの機能

MVPでは、一つの変換作業を次の順序で進められることを目標とする。

### 6.1 ファイルの取り込み

- Excel（`.xlsx`）またはCSVファイルを一つアップロードできる。
- 対象シートを選択できる。CSVの場合は文字コードや区切り文字の読み取り結果を確認できる。
- ファイル名、シート名、行数、列数、列名を確認できる。
- 約3,000行の架空デモデータを処理できる。
- 読み取れないファイルや未対応形式は、理由を示して受け付けない。

### 6.2 データの分析とプレビュー

- 元データの一部を表形式で表示できる。
- 列ごとに、推定されたデータ型、空欄数、値の例、値の種類数を確認できる。
- 空欄、不正な日付、想定外の値など、基本的な問題の候補を表示できる。
- 分析結果は確定事項ではなく、ユーザーが確認するための情報として扱う。

### 6.3 出力先テーブルと列の対応付け

- 複数の出力先テーブルを定義できる。
- 入力列を、各テーブルの出力列へ対応付けられる。
- 出力列ごとに、列名、データ型、必須かどうかを設定できる。
- 一つの入力データから、物件、会社、交通情報など複数のCSVへ分けられる。
- 対応付けされていない列を確認できる。

### 6.4 データの整形

- 前後の空白除去を設定できる。
- 空文字を欠損値として扱える。
- 日付形式を指定した形式へ統一できる。
- 「可／不可」「はい／いいえ」「1／0」などを、指定した真偽値表現へ変換できる。
- ユーザーが定義した値の対応表に基づいて、表記を統一できる。
- 元の値と変換後の値を比較できる。
- 元データそのものは書き換えず、変換結果を別データとして扱う。

### 6.5 入力値の検証

- 必須項目、データ型、日付形式、許可する値の一覧を検証できる。
- エラーがある行について、行番号、列名、元の値、エラー理由を表示できる。
- エラー件数を確認し、エラーのある行だけに絞り込める。
- エラーが残っている場合は、その状態を明示したうえで出力を制限できる。

### 6.6 重複候補の確認

- ユーザーが指定した一つまたは複数の列を使い、完全一致する重複候補を検出できる。
- 重複候補を一覧表示し、元の行を比較できる。
- 削除や統合は自動確定せず、ユーザーが採用する行を判断する。

### 6.7 テーブル別CSVの出力

- 検証済みの変換結果を、出力先テーブルごとのCSVとしてダウンロードできる。
- CSVには定義した列だけを、定義した順序で出力する。
- 出力前に、テーブルごとの行数とエラー件数を確認できる。
- 同じ入力と同じルールから、同じCSVを再作成できる。

### 6.8 作業状態の保存

- 変換作業の基本情報、列の対応付け、整形ルール、検証ルールを保存できる。
- 保存した作業を開き、設定内容を確認できる。
- 秘密情報を変換ルールやログへ保存しない。

## 7. MVPでは扱わない機能

- 本番環境を含む外部データベースへの直接接続、直接投入、更新、削除
- AIによる変換ルールの自動決定や、確認なしのデータ修正
- あいまい一致による高度な名寄せや、自動的な重複統合
- 複数ファイルの一括処理や、定期的な自動実行
- `.xls`、PDF、画像、Google Sheetsなど、`.xlsx`とCSV以外の入力
- 数式、マクロ、グラフ、セルの装飾など、表データ以外のExcel機能の維持
- ユーザー登録、ログイン、組織管理、細かな権限管理
- 複数ユーザーによる同時編集
- クラウドストレージや外部業務サービスとの連携
- 大規模データ向けの分散処理やストリーミング処理
- 変換ルールの版管理、承認ワークフロー、操作監査ログ
- 不動産業界固有の外部サービスや住所データベースとの連携

これらは将来の候補であり、MVPの完成前には実装しない。

## 8. 開発マイルストーン

MVPの機能は削減せず、各段階で動作と品質を確認できるように、次の順序で小さく実装する。各マイルストーンでは、対象機能に対応するテストを追加し、テスト、lint、型チェックが成功したことを確認してから次へ進む。

### 8.1 ファイル取込・分析

**実装対象**

- `.xlsx`とCSVのアップロード、対象シートの選択、CSVの読み取り結果の確認
- ファイル名、シート名、行数、列数、列名の取得
- 元データのプレビューと、推定データ型、空欄数、値の例、値の種類数の表示
- 未対応形式や読み取り失敗時の入力値検証とエラー表示

**完了条件**

- 架空のサンプルファイルを取り込み、元データを変更せずに基本情報と分析結果を確認できる。
- 不正なファイルを受け付けず、ユーザーが原因を判断できるエラーを表示できる。

### 8.2 整形・検証

**実装対象**

- 空白除去、欠損値、日付、真偽値、値の対応表による整形ルール
- 元の値と変換後の値の比較
- 必須項目、データ型、日付形式、許可値の検証
- エラー件数、行番号、列名、元の値、理由の表示と絞り込み

**完了条件**

- 指定したルールから同じ変換結果を再現でき、元データが書き換えられない。
- 正常な値とエラーのある値をテストで区別でき、画面でエラーの場所と理由を確認できる。

### 8.3 重複候補の確認

**実装対象**

- 一つまたは複数の指定列による完全一致の重複候補検出
- 重複候補と元の行の比較
- 採用する行の選択

**完了条件**

- 指定した条件に一致する候補だけを検出し、ユーザーの判断なしに削除や統合を行わない。
- 重複候補がない場合と複数ある場合の両方をテストで確認できる。

### 8.4 出力先定義・テーブル別CSV出力

**実装対象**

- 複数の出力先テーブルと、列名、データ型、必須設定の定義
- 入力列と出力列の対応付け、および未対応列の確認
- テーブルごとの行数とエラー件数の確認
- 定義した列と順序によるテーブル別CSVの出力

**完了条件**

- 一つの入力データを複数のテーブルへ分け、検証済みの結果をCSVとしてダウンロードできる。
- 同じ入力とルールから同じCSVを再作成でき、エラーが残る場合は出力を制限できる。

### 8.5 作業状態の保存

**実装対象**

- 変換作業の基本情報、列の対応付け、整形ルール、検証ルールの保存
- 保存した作業の再表示
- PostgreSQLのテーブル定義、SQLAlchemyのモデル、Alembicのマイグレーション

**完了条件**

- 保存した作業を開き直し、設定内容を確認して同じ処理を再開できる。
- 秘密情報を変換ルールやログへ保存せず、データベースの制約とテストで不正な状態を防止できる。

### 8.6 UI、テスト、ドキュメントの仕上げ

**実装対象**

- アップロードからCSV出力までの画面遷移、表示、操作性の調整
- 架空の約3,000件の不動産デモデータによる一連の動作確認
- 主要な変換処理、検証処理、API、画面操作の自動テスト
- GitHub Actionsによるテスト、lint、型チェック
- 環境構築、起動方法、デモ手順、制約事項のドキュメント

**完了条件**

- 本番データベースへ接続せず、架空データのアップロードからテーブル別CSV出力までのデモを完了できる。
- ローカル環境とGitHub Actionsでテスト、lint、型チェックが成功し、ドキュメントに従って環境と操作を再現できる。

## 9. 不動産データを使ったデモの流れ

デモでは、入力形式や表記を意図的にばらつかせた、約3,000件の架空の物件データを使用する。

1. ユーザーが架空の不動産Excelファイルをアップロードする。
2. アプリが、物件名、住所、建設会社、分譲会社、交通情報、URL、学校区、築年月、階数、ペット可否、タワーマンション判定、駐車場種別などの列を読み取る。
3. ユーザーが、空欄数、推定データ型、値の例、問題候補を確認する。
4. ユーザーが、入力列を物件、会社、交通情報、学校区、駐車場などの出力先テーブルへ対応付ける。
5. ユーザーが、空白除去、日付形式、真偽値、会社名や駐車場種別の表記統一ルールを設定する。
6. アプリがルールを適用し、元の値と変換後の値を並べて表示する。
7. アプリが必須項目、形式、許可値を検証し、問題のある行と理由を表示する。
8. ユーザーが、物件名と住所などの列を指定して完全一致の重複候補を確認し、採用する行を判断する。
9. ユーザーが、テーブルごとの行数とエラーがないことを確認する。
10. アプリが、物件、会社、交通情報などのテーブル別CSVを出力する。
11. ユーザーが出力CSVを確認する。本番データベースへの投入はデモに含めない。

## 10. 使用技術と採用理由

| 分類 | 使用技術 | 採用理由 |
| --- | --- | --- |
| Frontend | Next.js | 画面とルーティングの責務を整理しやすく、保守しやすいReactアプリの構成を作れるため。 |
| UI | React | アップロード、表、設定フォーム、エラー一覧など、状態が変化する画面を部品に分けて構築できるため。 |
| Language | TypeScript | データの形を型として表現し、フロントエンドでの値の取り違えを早期に見つけやすくするため。 |
| Styling | Tailwind CSS | 小さな単位で画面を作りながら、一貫したスタイルを適用しやすいため。 |
| Backend | Python / FastAPI | Pythonのデータ処理機能を活用でき、型情報と入力値検証を備えたAPIを構築しやすいため。FastAPIはAPI仕様書も自動生成できる。 |
| Database | PostgreSQL | 変換作業、テーブル定義、変換ルールなどの関連を持つデータを、制約を使って安全に保存できるため。 |
| ORM | SQLAlchemy | Pythonの型やクラスを使ってデータベース操作を整理し、業務処理とデータアクセスの責務を分けやすいため。 |
| Migration | Alembic | データベース構造の変更履歴をコードとして管理し、環境ごとに同じ変更を再現できるため。 |
| Frontend Test | Vitest | TypeScriptとの相性がよく、変換表示や画面部品の振る舞いを高速に確認できるため。 |
| Backend Test | Pytest | Pythonのテストを簡潔に記述でき、データ変換、検証、APIの動作を段階的に確認できるため。 |
| Environment | Docker Compose | フロントエンド、バックエンド、PostgreSQLを同じ手順で起動し、開発環境の差を減らすため。 |
| CI | GitHub Actions | テスト、lint、型チェックを自動化し、変更による問題を早期に検出するため。 |
| Runtime | mise（Node.js 24、Python 3.13） | 開発者ごとの実行環境のバージョン差を減らし、同じ条件で開発・確認できるようにするため。 |

Excel・CSVの読み書きなどに追加ライブラリが必要になった場合は、実装タスクに入る前に候補、目的、必要性を説明して選定する。本要件書の作成時点では、ライブラリを追加しない。

## 11. 完成と判断する基準

以下をすべて満たしたとき、MVPが完成したと判断する。

- 架空の約3,000件の不動産データを含む`.xlsx`ファイルをアップロードし、対象シートと基本情報を確認できる。
- CSVファイルについても、取り込みと基本情報の確認ができる。
- 列ごとの空欄数、推定データ型、値の例、値の種類数を確認できる。
- 複数の出力先テーブルを定義し、入力列と出力列を対応付けられる。
- 空白、日付、真偽値、値の対応表による整形を設定し、変換前後を比較できる。
- 必須項目、データ型、日付形式、許可値を検証し、行・列・理由が分かる形でエラーを確認できる。
- 指定した列による完全一致の重複候補を確認し、採用する行をユーザーが選べる。
- エラーのない変換結果を、定義したテーブルごとのCSVとして出力できる。
- 同じ入力データと同じルールを使った場合、同じ出力結果を再現できる。
- 元のアップロードデータが、整形処理によって直接書き換えられない。
- 不正な入力や処理失敗が、原因の分かるエラーメッセージとしてユーザーに示される。
- 主要な変換処理、検証処理、API、画面操作に対応する自動テストがある。
- テスト、lint、型チェックがローカル環境とGitHub Actionsで成功する。
- READMEなどの案内に従い、miseとDocker Composeを使って開発環境を再現できる。
- 本番データベースへ接続しなくても、アップロードからCSV出力までのデモを完了できる。

## 12. 個人情報・機密情報を扱う際の注意事項

- 開発、テスト、デモでは、実際の顧客情報、取引先情報、物件情報、個人情報を使用しない。実在するデータを加工したものではなく、架空のサンプルデータを作成する。
- APIキー、パスワード、データベース接続情報などを、ソースコード、サンプルデータ、ログ、Git履歴へ含めない。
- `.env`はGitへコミットせず、必要な環境変数名と用途だけを`.env.example`へ記載する。
- アップロードされた元ファイルと変換途中のデータは機密情報として扱い、必要な処理以外では表示、複製、出力しない。
- ログやエラーメッセージには、行全体や個人を特定できる値をそのまま記録しない。調査に必要な場合も、行番号、列名、処理IDなどを優先する。
- ファイル形式、拡張子、サイズ、行数を検証し、想定外のファイルを処理しない。
- ファイル名やセルの内容を信用せず、入力値として検証する。CSV出力では、表計算ソフトで数式として実行される可能性のある値にも注意する。
- 元ファイルや一時ファイルには保持期限を設け、不要になったデータを削除できる設計にする。
- ブラウザ、API、データベース、ファイル保存の各段階で、必要最小限のデータだけを扱う。
- 将来、実データを扱う場合は、利用目的、保存場所、保持期間、アクセス権、削除方法、暗号化、監査方法を事前に定め、組織の規程や適用法令を確認する。
- 出力CSVはユーザーが内容を確認してから利用する。アプリの出力を、確認せず本番データベースへ投入しない。

## 13. MVPの基本方針

- 自動化よりも、処理内容をユーザーが理解・確認できることを優先する。
- 元データを保護し、変換結果は別データとして作成する。
- 問題を自動的に隠したり修正したりせず、場所と理由をユーザーへ示す。
- 汎用的な仕組みを中心にし、不動産固有のルールをアプリ本体へ固定しない。
- 小さな機能単位で設計、実装、テストを行い、各段階で動作を確認する。
