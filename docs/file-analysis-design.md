# ファイル取込・分析 詳細設計

## 1. この文書の目的

この文書は、`docs/product-requirements.md`のマイルストーン「ファイル取込・分析」を実装する前に、Excel（`.xlsx`）とCSVの対応範囲、入力上限、型推定、分析結果、API、ファイル保持、安全対策、実装タスクの分割を確定するものである。

この機能は、アップロードされた表データの構造と基本的な傾向をユーザーが確認するための汎用機能とする。不動産固有の列名、値、検証ルールは埋め込まず、本番データベースへの投入も行わない。

## 2. 設計の基本方針

- 一度に一ファイルだけを受け付ける。
- アップロード受付と分析を分け、Excelの対象シートやCSVの読み取り設定を確認してから分析する。
- バックエンドの検証結果を信頼できる基準とし、拡張子やブラウザ側の検証だけを信用しない。
- 元ファイルは変更せず、サーバー生成IDを使って非公開領域に保存する。
- 分析結果は自動修正や業務上の確定判定ではなく、ユーザーが確認するための情報とする。
- 約3,000行の架空デモデータを安定して処理できる範囲に絞り、分散処理やジョブキューは導入しない。
- PostgreSQL未接続の段階では、短期ファイル保存と最小限のメタデータ管理だけをローカルファイル領域で行う。
- 開発、テスト、デモには実データを使用しない。
- 現在のMVPには認証・認可がないため、架空データ専用のローカル環境または利用者を限定したデモ環境として扱い、認証なしで不特定多数が利用できる形では公開しない。

## 3. ライブラリ選定

### 3.1 採用案

| 用途 | 採用する仕組み | 設計上の依存範囲 | 理由 |
| --- | --- | --- | --- |
| CSV解析 | Python標準ライブラリの`csv` | 追加依存なし | 引用符、区切り文字、引用符内改行を扱え、MVPの対応範囲に十分なため |
| 文字コード処理 | `codecs`などの標準ライブラリ | 追加依存なし | 対応文字コードを限定し、厳密なデコードを行うため |
| 型推定 | `datetime`、`decimal`、`re`などの標準ライブラリ | 追加依存なし | 保守的な型推定に十分なため |
| `.xlsx`のZIP事前検査 | 標準ライブラリの`zipfile` | 追加依存なし | 展開前にファイル数、展開後サイズ、圧縮率などを検査できるため |
| `.xlsx`解析 | `openpyxl` | `>=3.1.5,<4` | シート、セル型、数式セル、日付を扱え、read-onlyモードを利用できるため |
| XML攻撃への防御 | `defusedxml` | `>=0.7.1,<0.8` | 信頼できない`.xlsx`内のXMLを扱う際の防御を補うため |
| `multipart/form-data`受信 | `python-multipart` | `>=0.0.32,<0.1` | FastAPIでファイルアップロードを受信するために必要なため |

ここに記載するバージョンは設計上の許容範囲である。追加前に互換性と公開状況を再確認し、実装時に`uv.lock`へ解決結果を固定する。今回はライブラリを追加しない。

FastAPIではファイル全体を`bytes`として受け取らず、`UploadFile`を利用する。受信データは一定量までメモリ、それを超える場合は一時ファイルとして扱えるため、無条件に全内容をメモリへ読み込むことを避けられる。

### 3.2 他の候補との比較

| 候補 | 利点 | 欠点 | 判断 |
| --- | --- | --- | --- |
| `pandas` | 表形式の集計と型変換が容易 | 依存が重く、自動変換で元データの表現を変えやすい | 採用しない |
| `python-calamine` | 高速でApple Siliconを含む複数環境向けwheelがある | `openpyxl`より新しく、空行・空列の既定の扱いが元データ確認と合わない可能性がある | 採用しない |
| 文字コード自動判定ライブラリ | 多数の文字コードを推測できる | 誤判定があり、MVPの対応範囲が広がりすぎる | 採用しない |
| 標準`zipfile`とXMLパーサーだけで`.xlsx`を読む | 追加依存が不要 | Office Open XMLの解釈を自前で保守する範囲が大きすぎる | 採用しない |

### 3.3 `openpyxl`境界の型チェック

`openpyxl`を実装した際にmypyが必要とする型情報が不足する場合は、次の二案を比較して決定する。

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| `types-openpyxl`を開発依存へ追加する | ライブラリAPIを広く型チェックしやすい | 実際の`openpyxl`との型定義差や、追加依存の更新管理が発生する |
| `openpyxl`との境界を自前の型で包む | アプリ内へ外部ライブラリ固有型を広げず、必要な範囲だけ安定した型にできる | 境界変換コードと保守が必要になる |

依存追加前に実際のmypy結果と利用範囲を確認し、必要性が小さければ境界を自前の型で包む案を優先する。今回は`types-openpyxl`を含む依存を追加しない。

## 4. 対応する入力形式

### 4.1 CSV

#### 対応文字コード

- UTF-8
- UTF-8 with BOM
- CP932
- UTF-16 LEまたはBE。ただしBOMがある場合だけ対応する。

判定順序は次のとおりとする。

1. BOMを確認する。
2. BOMがない場合はUTF-8として厳密にデコードする。
3. UTF-8で失敗した場合はCP932として厳密にデコードする。
4. 置換文字で読み飛ばさず、どの方式でも読めなければ拒否する。

#### 対応区切り文字

- カンマ `,`
- タブ
- セミコロン `;`

`csv.Sniffer`の結果は確定値として信用せず、許可した候補の中で列数が安定するか再検証する。検出した文字コードと区切り文字はユーザーへ表示し、ユーザーが変更して再分析できるようにする。

#### 対応改行コード

- LF
- CRLF
- CR
- 引用符内の改行

改行コードが混在していても受け付けるが、分析結果にwarningを返す。

### 4.2 Excel

- `.xlsx`だけを受け付ける。
- `.xls`、`.xlsm`、`.xlsb`、PDF、画像などは拒否する。
- ワークシート名と表示状態をアップロード成功レスポンスで返す。
- 最初の表示シートを推奨選択として示すが、自動確定はしない。
- 分析時にはシート名を明示的に指定する。
- ヘッダーは1行目固定とし、ヘッダー位置の自動探索や複数行ヘッダーはMVP対象外とする。

## 5. 入力上限

| 対象 | 上限 |
| --- | ---: |
| アップロードファイル | 20 MiB |
| データ行数 | 10,000行（ヘッダーを除く） |
| 列数 | 200列 |
| `.xlsx`ワークシート数 | 20 |
| `.xlsx` ZIP内ファイル数 | 1,000 |
| `.xlsx`展開後合計サイズ | 100 MiB |
| ZIP圧縮率 | 最大100倍 |
| 列名 | 255文字 |
| 1セルまたはCSVフィールド | 100,000文字 |
| プレビュー | 先頭20データ行 |
| 値の例 | 列ごとに異なる値を最大3件 |
| APIで返す1表示値 | 200文字 |

約3,000行のデモデータは行数上限の3分の1以下であり、MVPの同期処理で扱える余裕を確保する。

`.xlsx`はZIP形式であるため、アップロードサイズだけでは安全性を判断しない。実際のファイルを展開する前に、ZIPの中央ディレクトリから次を検査する。

- 展開後サイズの合計
- ZIP内ファイル数
- 異常な圧縮率
- 暗号化されたエントリの有無
- `.xlsx`として必要な内部ファイルの有無
- 不正なパス名の有無

## 6. 表構造の扱い

### 6.1 ヘッダー

- 1行目を列名として扱う。
- 空文字または空白だけの列名は拒否する。
- 前後の空白を除いた結果が同じ列名は重複として拒否する。
- 元の列名自体は変更しない。
- Unicode正規化や大文字・小文字の統一は行わない。
- 重複や空列名のエラーには元の列位置を含める。

### 6.2 データ行

- ヘッダーだけでデータ行がない場合は`NO_DATA_ROWS`として拒否する。
- CSVの列数がヘッダーと異なる行は`ROW_WIDTH_MISMATCH`として拒否する。
- Excelでヘッダー範囲外に値がある行も`ROW_WIDTH_MISMATCH`として拒否する。
- 中間にある完全空行は空欄行として行数に含める。
- 末尾の完全空行は行数に含めない。
- API上の行番号は、ヘッダーを1行目とした元ファイル上の行番号とする。

### 6.3 空欄

空欄数には次を含める。

- CSVの長さ0のフィールド
- Excelの`None`
- Excelの空文字列

空白文字だけの値は自動的に空欄へ変更せず、`whitespace_only_count`として別に報告する。前後空白の除去や空白文字列の欠損値化は、後続の整形機能の責務とする。

### 6.4 数式セル

- 数式を実行・評価しない。
- 数式文字列を型推定と値の例に含めない。
- プレビュー値は`null`とする。
- 列ごとに`formula_count`を返す。
- `FORMULA_CELL_UNSUPPORTED`をwarningとして返す。
- 保存済みの計算結果にも依存しない。

## 7. 型推定

### 7.1 推定する型

- `empty`
- `boolean`
- `integer`
- `decimal`
- `date`
- `datetime`
- `string`
- `mixed`

空欄と数式セルは型推定の対象から除外する。

### 7.2 CSVの判定規則

各非空値を次の優先順位で判定する。

1. `true`または`false`（大文字・小文字を区別しない）を`boolean`とする。
2. 先頭ゼロのない符号付き整数を`integer`とする。
3. 桁区切りを含まない固定小数を`decimal`とする。
4. 厳密なISO形式`YYYY-MM-DD`を`date`とする。
5. ISO 8601形式の日時を`datetime`とする。
6. その他を`string`とする。

`1/0`、`はい/いいえ`、`可/不可`は型推定では真偽値としない。後続の整形機能で、ユーザーが定義した変換ルールとして扱う。`00123`は識別子の可能性があるため`string`とする。

### 7.3 Excelの判定規則

Excelセルが持つネイティブ型を優先する。

| セル値 | 推定型 |
| --- | --- |
| 真偽値 | `boolean` |
| 整数 | `integer` |
| 浮動小数または`Decimal` | `decimal` |
| 日付 | `date` |
| 日時 | `datetime` |
| 文字列 | `string` |
| 数式 | 推定対象外 |

### 7.4 列全体の型

- 全ての対象値が同じ型なら、その型とする。
- `integer`と`decimal`の組み合わせは`decimal`とする。
- `date`と`datetime`の組み合わせは`datetime`とする。
- それ以外の複数型は`mixed`とする。
- 非空かつ非数式の値がなければ`empty`とする。

推定結果は確認用であり、自動変換や業務上の正しさを保証しない。

## 8. 分析結果

### 8.1 ファイル全体

- 元の表示ファイル名
- ファイル形式
- ファイルサイズ
- SHA-256チェックサム
- 選択シート
- CSVの文字コード、区切り文字、改行コードの検出結果
- データ行数
- 列数
- 列名
- 列ごとの分析結果
- 先頭20行のプレビュー
- warning一覧
- 分析に適用した上限値

### 8.2 列ごと

```json
{
  "index": 1,
  "name": "価格",
  "inferred_type": "integer",
  "blank_count": 12,
  "whitespace_only_count": 2,
  "distinct_count": 1540,
  "formula_count": 0,
  "formula_like_count": 0,
  "examples": [
    {
      "value": "12000000",
      "truncated": false
    }
  ],
  "issues": [
    {
      "code": "MIXED_TYPES",
      "count": 3
    }
  ]
}
```

- `distinct_count`は非空かつ非数式の値について集計する。
- `formula_like_count`は、CSVの型推定で`string`と判定された値だけを対象とする。`-100`など正常な数値、日付、日時として判定できる値は、先頭文字が数式の開始文字と同じでも対象外とする。
- 値の例は異なる値を最大3件まで返す。
- 200文字を超える表示値は打ち切り、`truncated: true`を返す。
- 期待する型や許可値が未定義の段階では、「不正な日付」や「想定外の値」を業務エラーとして断定しない。
- `mixed`、空白だけの値、数式らしいCSV値などを問題候補として示す。

## 9. 同期処理と非同期処理

| 方式 | 利点 | 欠点 |
| --- | --- | --- |
| 同期処理 | 実装と画面状態が単純で、追加インフラが不要 | 完了までHTTPリクエストが継続する |
| 非同期ジョブ | 長時間処理、再試行、進捗表示に向く | 状態保存、queue、worker、状態確認APIが必要になる |

MVPでは同期処理を採用する。対象が最大20 MiB、10,000行で、主なデモが約3,000行であるため、ジョブキューやworkerは追加しない。

CPU処理やファイル解析によってFastAPIのイベントループを塞がないことを実装要件とする。通常の`def`ルートを使うか、thread poolへ処理を移すかなどの具体的な方法は、処理境界とテスト方法を確認して実装時に決定する。

実測で分析が継続的に10秒を超える場合や、入力上限を大幅に拡大する場合は非同期化を再検討する。

## 10. 元ファイルとメタデータの保存

### 10.1 PostgreSQL接続前の保存先

バックエンド専用の名前付きDocker Volumeへ次の形で保存する。

```text
/data/uploads/
├── {file_id}.source
└── {file_id}.json
```

メタデータJSONには次だけを保存する。

- file ID
- 元の表示名
- ファイル形式
- ファイルサイズ
- SHA-256チェックサム
- `created_at`
- `expires_at`
- シート一覧またはCSV検出結果

`created_at`と`expires_at`は、どちらもタイムゾーン情報を持つUTC日時として保存し、期限判定でもUTC日時同士を比較する。

分析結果はPostgreSQL接続前には保存せず、要求ごとに元ファイルから再生成する。将来、JSONメタデータ管理をPostgreSQL repositoryへ置き換えられる境界にする。

### 10.2 保存手順

1. 元ファイル用の一時ファイルへチャンク単位で書き込む。
2. 書き込みと同時にサイズとSHA-256を計算する。
3. 形式、ZIP構造、シート一覧またはCSVデコードを検証する。
4. メタデータJSONも専用の一時ファイルへ書き込み、内容を検証する。
5. 元ファイルとメタデータJSONを、それぞれの確定ファイル名へatomic renameする。
6. 途中で失敗した場合は、関連する一時ファイルに加え、この受付処理ですでにrename済みの元ファイルまたはメタデータJSONも削除し、片方だけを残さない。

元の表示ファイル名を保存先パスとして使用しない。

### 10.3 保持期限と参照可否

- 正常受付した元ファイルの保持期限は受付から24時間とする。
- `created_at`と`expires_at`および現在日時は、タイムゾーン情報を持つUTC日時として比較する。
- 全てのfile IDを使うAPIアクセスで、処理開始前に`expires_at`を必ず検証する。
- 現在日時が`expires_at`以上なら、物理ファイルが残っていても参照・分析を許可しない。
- 不存在と期限切れは内部状態を推測されにくくするため、どちらも`404 Not Found`として同じ安全なエラー形式を返す。
- `.part`ファイルは処理成功時または失敗時に直ちに削除する。
- 受付段階で破損と判断したファイルは保存しない。
- 有効なExcelで特定シートの分析だけに失敗した場合は、別シートを試せるよう期限まで保持する。

アプリ起動時と新規アップロード時に行うcleanupは、期限切れファイルを物理削除する機会である。cleanupの実行時刻にかかわらず、APIアクセス時の`expires_at`検証が24時間後の利用不可を保証する。参照可否の保証と物理削除の機会を別の仕組みとして扱う。

バックグラウンドschedulerはMVPでは追加しない。

## 11. API設計

### 11.1 ファイルアップロード

```http
POST /api/v1/files
Content-Type: multipart/form-data
```

フォーム項目:

- `file`: 必須。1ファイルだけを受け付ける。

成功時は`201 Created`を返す。

Excelの例:

```json
{
  "file_id": "9e7e21c8-0000-4000-8000-000000000000",
  "display_name": "sample.xlsx",
  "format": "xlsx",
  "size_bytes": 182340,
  "checksum_sha256": "...",
  "expires_at": "2026-08-13T12:00:00Z",
  "sheets": [
    {
      "name": "物件",
      "state": "visible",
      "suggested": true
    }
  ],
  "csv_detection": null,
  "warnings": []
}
```

CSVでは`sheets`を空配列とし、次のような検出結果を返す。

```json
{
  "format": "csv",
  "sheets": [],
  "csv_detection": {
    "encoding": "utf-8",
    "delimiter": ",",
    "newline_types": ["CRLF"],
    "warnings": []
  }
}
```

### 11.2 ファイル分析

```http
POST /api/v1/files/{file_id}/analysis
Content-Type: application/json
```

Excelのrequest:

```json
{
  "sheet_name": "物件"
}
```

CSVのrequest:

```json
{
  "csv_options": {
    "encoding": "utf-8",
    "delimiter": ","
  }
}
```

成功時は`200 OK`を返す。

```json
{
  "file_id": "9e7e21c8-0000-4000-8000-000000000000",
  "source": {
    "format": "xlsx",
    "sheet_name": "物件"
  },
  "table": {
    "row_count": 3000,
    "column_count": 12,
    "columns": []
  },
  "preview": {
    "limit": 20,
    "rows": []
  },
  "warnings": []
}
```

アップロードと分析を分けることで、Excelではシート一覧、CSVでは検出した文字コードと区切り文字を確認・修正してから分析できる。

### 11.3 エラーレスポンス

```json
{
  "error": {
    "code": "DUPLICATE_COLUMN_NAME",
    "message": "重複する列名があります。",
    "details": [
      {
        "column_indexes": [2, 5],
        "column_name": "住所"
      }
    ],
    "trace_id": "..."
  }
}
```

| HTTP status | 用途 | 例 |
| --- | --- | --- |
| `400 Bad Request` | リクエストとして処理できるがファイル内容が基本条件を満たさない | 空ファイル、ヘッダーだけのファイル、行幅不一致、空列名、重複列名 |
| `404 Not Found` | 対象を参照できない | file ID不存在、保持期限切れ。両者を同じ応答にする |
| `413 Content Too Large` | 処理資源に関わる容量上限超過 | アップロードサイズ、ZIP展開後合計サイズ、ZIP内ファイル数、異常な圧縮率、1フィールドサイズ |
| `415 Unsupported Media Type` | 入力形式をサポートしない | 未対応拡張子、実体が未対応形式、未対応文字コード |
| `422 Unprocessable Content` | 指定や表構造上の上限が処理条件を満たさない | 存在しないシート、許可されないCSV設定、行数、列数、シート数の上限超過 |
| `500 Internal Server Error` | 予期しない内部エラー | 実装上の想定外の処理失敗 |

APIレスポンスに内部ファイルパス、スタックトレース、秘密情報、セル行全体を含めない。

## 12. 安全上の注意

- 拡張子とContent-Typeだけでファイル形式を判断しない。
- `.xlsx`のZIP構造を`openpyxl`へ渡す前に検証する。
- 暗号化されたファイル、マクロ形式、未対応形式を拒否する。
- 外部リンクを読み込まず、数式を実行しない。
- ログへセル値や元ファイル名全体を記録しない。
- frontendではプレビュー値をHTMLとして挿入せず、Reactの通常テキストとして表示する。
- CSVの入力値は分析時に書き換えない。
- 認証・認可を実装する前は、架空データ専用のローカル環境または利用者を限定したデモ環境でのみ動かし、不特定多数へ公開しない。

CSVの型推定で`string`と判定された値が`=`、`+`、`-`、`@`、タブ、改行など数式として解釈され得る文字から始まる場合は、`formula_like_count`として警告する。`-100`など正常な数値、日付、日時として判定できる値は対象外とし、警告の過剰検出を避ける。入力時には値を変更しない。出力CSVの具体的な無害化は、表計算ソフトでの表示とデータベース取込の両方への影響を比較し、CSV出力マイルストーンで確定する。

列の意味を知らない段階での自動マスキングは誤判定が多いため、MVPの分析機能には追加しない。架空データだけを使用し、表示行数と表示文字数を制限する。
